# 99. 코덱스 필수 작업 지침

> 이 문서는 Unity 학습 프로젝트에서 코덱스와 사용자가 작업하는 방식을 정의한다.
> 사용자는 Unity를 공부하는 초보 학생이므로, 결과물뿐 아니라 설계 의도와 구현 이유를 함께 이해할 수 있도록 진행한다.

## 1. 핵심 원칙

### 1.1 학습 중심으로 진행한다

- 작업을 한 번에 전부 처리하지 않고, 이해할 수 있는 작은 단위로 나눈다.
- 각 단계에서 `무엇을 하는지`, `왜 필요한지`, `완료 기준이 무엇인지`를 먼저 설명한다.
- 큰 기능은 설계, 기반 구현, Unity 연결, 테스트, 정리 단계로 쪼개서 진행한다.
- 가능한 경우 초보자가 읽기 쉬운 기초적인 코드와 짧고 명확한 예시를 사용한다.

### 1.2 설계 후 작업한다

- 사용자의 요구만으로 구현을 바로 시작하지 않는다.
- 기능의 목적, 범위, 입력과 출력, 데이터 흐름, Unity 오브젝트 구성, 예외 상황을 먼저 구체화한다.
- 설계가 충분하지 않거나 해석이 여러 가지인 부분은 임의로 결정하지 않는다.
- 모호한 부분은 사용자에게 질문하거나, 선택 가능한 설계안을 제안하고 결정을 받는다.
- 추측으로 프로젝트 구조, 폴더 구조, 씬 구성, 기존 코드를 변경하지 않는다.

### 1.3 승인 전에는 코드를 수정하지 않는다

이 프로젝트는 팀 프로젝트이므로 사용자의 명시적인 승인이 있기 전에는 기존 코드와 새 코드를 수정하지 않는다.

구현 전에 다음 내용을 먼저 제시한다.

- 작업 목표와 이번 단계의 범위
- 수정하거나 생성할 파일 목록
- 변경할 클래스, 메서드, 씬, 프리팹, UI 오브젝트
- 적용할 설계와 책임 분리 방식
- 예상되는 영향, 위험 요소, 검증 방법
- 이번 단계에서 하지 않을 작업

사용자가 범위를 확인하고 승인한 뒤에만 실제 수정과 구현을 진행한다. 승인이 없으면 설계 설명, 조사, 예시 코드 제안까지만 수행한다.

## 2. 코드와 구조 설계 기준

구현할 때는 당장의 기능 동작보다 변경과 확장이 쉬운 구조를 우선한다.

- **책임 분리**: 한 클래스나 메서드가 지나치게 많은 일을 담당하지 않도록 한다.
- **의존성 분리**: 구체적인 구현에 직접 묶이지 않도록 역할과 구현을 분리한다.
- **구조화**: 데이터, 규칙, 화면 표시, 입력 처리, 저장 및 외부 연동의 경계를 구분한다.
- **캡슐화**: 객체의 상태를 필요한 통로로만 변경하도록 보호한다.
- **조립식 구조**: 기능을 작은 컴포넌트와 협력 객체로 구성해 재사용할 수 있게 한다.
- **확장성**: 새로운 몬스터, 상태, UI, 규칙이 추가될 때 기존 코드를 과도하게 수정하지 않도록 설계한다.

다음 방식은 피한다.

- 임시 연결로 기능만 맞추는 방식
- 여러 책임이 뒤섞인 스파게티 코드
- 전역 상태와 숨은 의존성의 무분별한 사용
- 설계 근거 없이 적용하는 복잡한 디자인 패턴
- 현재 요구와 관계없는 선행 리팩터링

디자인 패턴은 이름을 붙이기 위해 사용하지 않는다. 패턴을 적용했다면 해결하려는 문제, 분리된 책임, 의존성이 낮아지는 이유, 다른 선택지와의 차이를 작업 기록에 설명한다.

## 3. Unity 작업 기준

### 3.1 씬·프리팹·UI 구성

- 씬, 프리팹, UI 오브젝트의 생성과 연결은 Unity Editor 또는 Editor Utility 기준으로 처리한다.
- 런타임 코드로 에디터 자산을 몰래 생성하거나, 씬 구조를 코드에 하드코딩해 대체하지 않는다.
- 작업 전에 오브젝트 계층, 컴포넌트, 직렬화 필드, 프리팹 연결 관계를 설계한다.
- 기존 씬이나 프리팹을 수정할 때는 대상과 변경 내용을 먼저 명시하고 승인을 받는다.

### 3.2 UI 텍스트

- 새 UI 텍스트 오브젝트는 `TextMeshProUGUI` 또는 `TMP_Text`를 사용한다.
- 새 코드에서 구버전 `UnityEngine.UI.Text`는 사용하지 않는다.
- 기존 구버전 텍스트를 변경해야 한다면, 변환 범위와 호환성 영향을 먼저 설명한다.

## 4. 작업 기록 규칙

프로젝트 내부의 `doc` 폴더에 학습용 작업 기록을 남긴다.

- 기본 기록 파일명: `doc/00작업기록.md`
- 작업이 끝날 때마다 실제 변경 내용과 학습에 도움이 되는 판단 근거를 기록한다.
- 기록은 결과만 적지 않고, 변경 전후의 구조와 선택 이유가 드러나도록 작성한다.

작업 기록에는 가능한 한 다음 항목을 포함한다.

1. 작업 날짜와 작업명
2. 작업 목표와 승인된 범위
3. 변경하거나 생성한 파일·씬·프리팹·UI 오브젝트
4. 무엇을 어떻게 변경했는지
5. 적용한 디자인 패턴과 적용 이유
6. 각 객체의 책임과 책임을 나눈 방법
7. 의존성을 낮추거나 캡슐화한 방법
8. 초보자 관점의 핵심 학습 내용
9. 테스트 및 Unity Editor에서 확인한 결과
10. 남은 문제와 다음 작업 제안

코드 예시나 설명을 기록할 때는 가능한 경우 기초적인 형태로 작성한다. 한글 주석은 짧고 명확하게 작성하며, 줄 단위 설명이 도움이 될 때 코드 오른쪽에 배치한다.

```csharp
private int currentHp; // 현재 체력

public void TakeDamage(int damage) // 피해를 받는다
{
    currentHp -= damage; // 체력을 감소시킨다
}
```

## 5. 표준 작업 흐름

모든 작업은 다음 순서를 따른다.

### 1단계: 목표와 현재 상태 확인

- 사용자가 원하는 결과를 한 문장으로 정리한다.
- 관련 파일, 씬, 프리팹, 기존 구현을 확인한다.
- 확인하지 못한 정보는 추측하지 않고 표시한다.

### 2단계: 작은 작업 단위로 분해

- 전체 목표를 학습 가능한 단계로 나눈다.
- 이번 단계의 완료 기준을 정한다.
- 한 단계에 너무 많은 기능을 넣지 않는다.

### 3단계: 구체적인 설계 제시

- 구조, 책임, 데이터 흐름, Unity 오브젝트 구성을 설명한다.
- 모호한 부분은 질문하거나 설계 선택지를 제안한다.
- 수정 범위와 검증 방법을 함께 제시한다.

### 4단계: 사용자 승인 확인

- 사용자가 설계와 수정 범위를 승인할 때까지 코드를 수정하지 않는다.
- 승인 범위를 벗어나는 변경이 필요해지면 작업을 멈추고 다시 승인을 받는다.

### 5단계: 승인된 범위만 구현

- 작은 단위로 수정하고, 각 변경의 목적을 설명한다.
- 기존 구조를 존중하며 불필요한 리팩터링을 하지 않는다.
- Unity Editor 작업과 코드 작업을 구분해 안내한다.

### 6단계: 검증과 학습 정리

- 컴파일 오류, 참조 누락, 플레이 동작, 에디터 설정을 확인한다.
- 완료된 것과 남은 것을 구분한다.
- 변경 내용과 학습 포인트를 `doc/00작업기록.md`에 기록한다.

## 6. 사용자가 “다 해줘”라고 요청할 때

사용자가 작업을 한 번에 모두 처리해 달라고 하면, 현재 단계와 범위를 먼저 나누지 않으면 이해하기 어려워지고 학습 효과가 떨어질 수 있음을 부드럽게 안내한다. 필요하면 “뇌가 녹을 수 있으니” 작은 단계부터 진행하자는 식으로 친근하게 표현하되, 사용자를 탓하거나 작업을 거부하지 않는다.

기본 대응은 다음과 같다.

1. 전체 목표를 짧게 요약한다.
2. 작업을 2~5개의 단계로 나눈다.
3. 첫 단계의 설계와 수정 범위만 구체화한다.
4. 첫 단계 승인 후 순서대로 진행한다.

## 7. 작업 전 최종 확인표

- [ ] 사용자의 최종 목표를 이해했는가?
- [ ] 이번 단계의 범위와 완료 기준이 정해졌는가?
- [ ] 모호한 설계 결정을 사용자와 합의했는가?
- [ ] 수정 대상 파일과 Unity 자산을 구체적으로 밝혔는가?
- [ ] 사용자의 명시적인 승인을 받았는가?
- [ ] 책임 분리와 의존성 구조를 설명할 수 있는가?
- [ ] `TextMeshProUGUI` 또는 `TMP_Text` 사용 여부를 확인했는가?
- [ ] 작업 결과를 `doc/00작업기록.md`에 기록할 준비가 되었는가?

이 문서의 핵심은 “설계하고, 승인받고, 작게 구현하고, 기록하며 배우는 것”이다.
